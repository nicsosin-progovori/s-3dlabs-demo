# Отдельная доставка списка видов и настроек камер

Страница `/bottle.html` получает виды отдельным JSON-запросом. Идентификаторы,
названия, порядок кнопок, параметры и вид по умолчанию не встроены в GLB,
skin manifest или JavaScript-сборку этой страницы.

Текущий каталог — schemaVersion 3 / revision v03. Корневые states описывают
12 прежних видов корпуса; lidStates — 9 прежних видов крышки для трёх состояний.
Каждый lidStates.<state> имеет тот же формат defaultView / views. Активный набор
выбирается по getDecoration().surface, подписи — по языку страницы. Он явно выбирает
`frameTarget: composition` для всей группы или `primary` для детали основного
участника. Общий расчёт центра / преобразований —
[COMPOSITION_CAMERAS.md](COMPOSITION_CAMERAS.md). Каталоги schemaVersion 1 / 2 сохранены
в совместимости; художественные параметры прежних 12 видов не изменились.

## Источник и HTTP

Канонический файл — `config/camera-views/bottle.json`.
Node обслуживает `GET /api/camera-views/bottle`; отдельный серверный процесс
не требуется. `server/cameraViews.mjs` читает и валидирует файл при каждом запросе.
Изменение файла не требует `vite build` или перезапуска Node. В открытой странице
список обновляется через `reloadViews()` либо при следующем открытии страницы;
автоматического polling нет. Новая версия конфигурации получает новый `revision`.

- `GET`: 200, JSON, `ETag`, `X-Camera-Views-Revision`, `Cache-Control: no-cache`.
- `HEAD`: те же метаданные без тела; совпадающий `If-None-Match` даёт 304.
- Другой метод: 405. Неизвестная модель: 404.
- Отсутствующий, повреждённый, несовместимый или слишком большой файл: 503.
  В ответ не выводятся путь сервера и содержимое ошибочного файла.

Объём JSON ограничен 64 КиБ; на состояние допускается до 32 видов. Маршрут
метаданных не загружает GLB / скины, не запускает Chromium и не занимает очередь PNG.
Клиент запрашивает актуальные данные с `cache: no-store`, таймаут — 30 секунд.
При отдельном frontend origin API задаётся meta-настройкой из
[BOTTLE_API.md](BOTTLE_API.md); формат каталога и независимость загрузки не меняются.

## Формат

Полный рабочий пример — [bottle.json](../config/camera-views/bottle.json).
Сокращённая форма записи одного вида:

```json
{
  "id": "overview",
  "label": {"de": "Hero", "en": "Hero"},
  "camera": {
    "azimuth": 24, "elevation": -0.05,
    "fov": 26, "roll": -2,
    "subject": [0.12, -0.015], "margin": 0.95,
    "near": 0.025, "far": 100, "zoom": 1
  }
}
```

Корень содержит `schemaVersion: 3`, `modelId: "bottle"`, `revision`, `compatibility`
и `states` / `lidStates`. В версиях 1 / 2 lidStates отсутствует, при выборе крышки
используется основной states; это совместимость старого каталога, а не встроенные
в JS камеры. Обязательные состояния — `closed`, `open`, `lying`. Каждое содержит
упорядоченный массив `views` и `defaultView`: существующий id либо `null`.
Пустой массив с `null` допустим. Id не привязаны к TypeScript enum: новые названия,
число и порядок видов меняются в данных. Id уникален внутри состояния.

`compatibility` фиксирует `poseContract: "bottle-poses-v01"`, `focusUnits: "millimetres"`,
вертикаль `up: "Y"`, фронт `front: "+Z"`. Это договор координат текущего rig;
изменение геометрии, pivot или поз требует проверки и обновления договора.
Он не заменяет проверку совместимости модели по её SPEC.

| Параметр | Значение |
| --- | --- |
| `azimuth` | Поворот вокруг вертикали, градусы, −360…360 |
| `elevation` | Отношение подъёма к горизонтальному удалению, −5…5 |
| `fov` | Вертикальный угол обзора, 5…100°, по умолчанию 28 |
| `roll` | Крен кадра, −180…180°, по умолчанию 0 |
| `subject` | Смещение композиции в долях кадра, два числа −0,4…0,4 |
| `margin` | Запас вписывания, 0,5…2; по умолчанию 1,12 |
| `focusMm` | Необязательные `min` / `max` XYZ зоны крупного плана в миллиметрах |
| `frameTarget` | `composition` — общий вид группы; `primary` — основной участник |
| `near`, `far`, `zoom` | Оптика камеры; по умолчанию 0,025 / 100 / 1 |

Ограничения оптики совпадают с публичным `setCamera`. Для лежащей позы fitter
сам добавляет смещение основания rig к `focusMm`; записывать его повторно нельзя.
`focusMm` относится к primary и преобразуется вместе с ним и корнем композиции;
с `frameTarget: composition` он несовместим. Без явного frameTarget в v1 значение
выводится по наличию focusMm. Размер viewer и общие границы участников в позе
преобразуют описание в `position / target`. Zoom учитывается при вписывании.
Так один JSON работает на телефоне и desktop. Общий алгоритм вписывания остаётся
кодом; художественные параметры и список видов находятся в JSON.

Общий валидатор — `shared/cameraViewsContract.mjs` с типами `.d.mts`.
Сервер и клиент отклоняют некорректный каталог целиком; неизвестные поля,
повторяющиеся id, нечисловые параметры и неверные границы не применяются частично.
Каталог содержит только данные, без функций, исполняемых выражений и URL ассетов.

## Независимая загрузка и обновление

`src/cameraViews.ts` управляет отдельной загрузкой. Viewer и панель подписываются
на её снимок; модель начинает свою прежнюю цепочку low → final независимо.

1. Пока каталога нет, сцена использует общее автоматическое вписывание.
   Подмены списком старых зашитых пресетов нет.
2. Если JSON успел до первого показа low, стартовый кадр использует `defaultView`.
   Доставленный v01 сохраняет все 12 прежних камер для трёх состояний.
3. Если JSON задержался до показа модели, его получение добавляет кнопки,
   сохраняя фактическую камеру. Ручное вращение, `setCamera`, состояния, скины
   и серверный PNG работают без списка видов.
4. При первом отказе кнопки видов отсутствуют, панель сообщает об ошибке.
   `ready` модели успешно завершается; `viewsReady` отклоняется отдельно.
5. Во время обновления доступны последние корректные виды. Ошибка обновления
   сохраняет их. Успех атомарно обновляет список без смены камеры, позы, скина,
   WebGL-контекста и повторной загрузки GLB / карт. При изменении параметров
   выделение прежней кнопки снимается, если фактическая камера больше не совпадает.
6. Более новый запрос отменяет старый. Поздний ответ старого запроса не может
   перезаписать актуальные данные. Размонтирование отменяет загрузку.

После явной смены состояния используется `defaultView` нового состояния
из текущего каталога; без него — автоматическое вписывание.

## Публичный API

```js
const app = window.appName3DVisualisation;
await app.viewsReady;        // независимо от app.ready модели
const raw = app.getViewCatalog(); // копия исходного каталога либо null
await app.ready;
const views = app.getViews(); // id, label, camera для текущей позы и размера
await app.setCamera(views[0].camera);
await app.reloadViews();     // новый запрос без перезагрузки модели
```

`viewsReady` — Promise последней начатой попытки. `reloadViews()` возвращает
Promise этой попытки; он не входит в очередь модельных команд и не меняет busy
сцены. При отказе следует обработать rejection. `getViewCatalog()` доступен
до готовности модели и возвращает изолированную копию. `getViews()` до готовности
геометрии / камеры или без каталога возвращает `[]`; его нужно читать заново
после изменения состояния, размера или списка. Поле `label` добавлено к прежним
`id` / `camera`. Кнопки вызывают единственный публичный `setCamera(camera)`.

Серверный PNG версии 5 получает фактическую камеру с матрицей проекции,
состояние, скин, сцену и состав / преобразования композиции, а не id пресета.
Worker не запрашивает каталог видов;
недоступность JSON не блокирует рендер.

## Эксплуатация и границы переноса

В комплект Node-приложения входит `config/camera-views/` рядом с `dist/`,
`server/` и `shared/`. Публикация одного `dist/` не доставляет этот API.
Файл обновляется целиком, желательно атомарной заменой на том же filesystem,
после проверки схемы. При ошибке уже открытые страницы сохраняют последний
правильный список, новые страницы остаются с рабочей моделью без кнопок видов.

Реализован адаптер бутылки на `/bottle.html`. Старый каталог / пара сохраняют
камеры в `src/bottleViews.ts`; остальные модели пока не перенесены. Для нового
товара нужны отдельный каталог, собственный договор поз / координат и fitter,
проверенные на low, final, всех состояниях и размерах экрана.

Проверки: `npm run test:bottle:cameras` и `tests/bottle-cameras.spec.ts`.
Фактические результаты прогона фиксируются в [плане](BOTTLE_API_PLAN.md).

# Страница бутылки: API и серверный PNG

Общие требования к low → final для всех моделей и план перевода существующих —
[MODEL_DELIVERY_STANDARD.md](MODEL_DELIVERY_STANDARD.md). Этот документ описывает
действующую реализацию и API бутылки.

Реализована [отдельная доставка скинов](SKIN_DELIVERY_DESIGN.md): geometry GLB,
skin manifest и общие low / final PNG. Доступны setSkin / getSkin / getSkins;
серверный контракт версии 5 учитывает выбранные скин, сцену, композицию, логотип и нанесение.

[Список видов и настройки камер](CAMERA_VIEW_DELIVERY.md) доставляются отдельно:
`GET /api/camera-views/bottle`, исходник `config/camera-views/bottle.json`.
Названия, порядок и параметры меняются без пересборки frontend.

[Камеры рассчитываются по композиции](COMPOSITION_CAMERAS.md): общий центр,
root / member-преобразования, весь состав либо крупный план primary. Добавлены
getComposition, getCompositionBounds, setComposition; по умолчанию остаётся одна бутылка.

[Свет, окружение и тени](SCENE_DELIVERY.md) также доставляются отдельно.
`/api/scenes/default` выбирает активный профиль из `config/scenes/default.json`;
версионированные JSON-профили находятся в `config/scenes/<id>/<revision>/`.

## Страница и компонент

`src/BottleApiPage.tsx` содержит интерфейс. `src/BottleVisualisation.tsx` —
самостоятельный viewer без HTML-элементов управления. Панель находится рядом,
на телефоне — ниже. Внутри viewer остаются только вращение / zoom жестами.

По отдельному запросу владельца после задачи 1 восстановлены девять цветов,
собственный логотип, выбор корпуса / крышки, способы нанесения и DE/EN.
Первоначальное ограничение UI только состояниями / видами / PNG больше не действует.
Три состояния, геометрия, кинематика и принятая студия сохранены. По умолчанию —
чёрный скин, цветной демонстрационный логотип с лазерной гравировкой на корпусе.

Все предметные элементы вызывают публичный API; язык относится к оболочке страницы.
DE/EN переводит заголовки, формы, статусы / ошибки, подписи цветов и виды из JSON.
Выбор языка хранится в `s3dlabs-language`, как в прежнем контуре; обновляются lang,
title и description документа. Смена языка не пересоздаёт viewer и не сбрасывает
состояние, камеру, скин или логотип. По умолчанию используется немецкий.
Настройки предмета действуют до перезагрузки страницы; серверный файл логотипа
хранится отдельно и переживает перезапуск backend.

Панель показывает все разделы без внутренней прокрутки и растёт по содержимому,
включая дополнительные поля метода / статусы. На desktop 3D-превью растягивается
по той же строке grid: верхняя и нижняя границы обеих карточек совпадают.
Заголовки, разделители и поля панели имеют общий внутренний отступ; PNG идёт
последним разделом в обычном потоке. На телефоне карточки стоят друг под другом,
превью сохраняет отдельную ограниченную высоту, панель показывается целиком. Прежняя страница товаров остаётся по адресу `/`.

## Постепенная загрузка бутылки — задача 2

На `/bottle.html` первыми загружаются `bottle-geometry-low-v01.glb`, manifest
выбранного скина и его low-карты. Закрытая сборка воспроизводит все три состояния
существующим контроллером. Затем фоном загружаются `bottle-geometry-final-v01.glb`
и final-карты того же скина; сервер непосредственно использует этот final-пакет.
Старая страница товаров продолжает загружать исходный HQ.

| Ассет | GLB, байты | Пакет с manifest / PNG, байты | Треугольники |
| --- | ---: | ---: | ---: |
| Low | 157 476 | 196 162 | 6 082 |
| Final | 506 284 | 1 345 114 | 21 980 |
| Исходный HQ-эталон | 5 816 648 | 5 816 648 | 57 928 |

Пакеты рассчитаны для чёрного скина. Общая цепочка — 1 534 577 байт,
manifest загружается один раз. Другие цвета переиспользуют те же карты.
Это объём моделей / материалов, а не всего frontend. Встроенные low / HQ
191 392 / 1 340 356 байт сохранены как источники упаковки и эталоны;
новая страница их не запрашивает. Геометрия, UV и исходные PNG отделены
без изменения байтов содержимого.

Порядок загрузки:

1. Загрузить low-геометрию и её скин, подготовить окружение / тени и первый кадр.
2. Завершить публичный `ready`: пользователь уже может менять состояния, виды,
   вращать бутылку и скачивать PNG.
3. После первого показа начать final с `fetch priority: low`; GLB загружается
   кусками по 256 KiB, отдельные карты — общей очередью до двух запросов.
   Production-сервер поддерживает byte ranges; таймаут
   действует на кусок, а не на всю большую модель.
4. Загрузить текстуры в GPU с уступками отрисовке и вводу; предварительно
   скомпилировать обычные HQ-материалы и вариант для плавного перехода.
5. Дождаться завершения предметной / камерной анимации и жеста пользователя.
   Заменить только отображаемую геометрию, сохраняя контроллер, позу, камеру,
   состояние, нанесение, освещение и тот же Canvas / WebGL-контекст.
6. Плавно проявить HQ-карты за 320 мс. Смешивание непрозрачных материалов
   происходит в shader, без снимка canvas и двойной полупрозрачной бутылки.
   При reduced motion применяется конечный материал сразу. После перехода
   возвращаются обычные HQ-шейдеры, уже подготовленные в GPU.

Ошибка фонового HQ не блокирует страницу: low остаётся рабочей. Фоновые запросы
отменяются при закрытии viewer. PNG всегда рассчитывается на сервере по финальной
оптимизированной HQ-модели, даже если клиент пока показывает low. Публичный API
задачи 1 сохранён.

Low и финальный HQ имеют разные файлы и SHA-256 в URL; исходный HQ и
`prepared-v02.blend` не перезаписываются. Воспроизводимая подготовка —
`scripts/prepare-bottle-low.py`, editable source — `models/bottle/prepared-low-v01.blend`,
метаданные исходного low — `models/bottle/low-v01.json`. Упаковка скинов —
`npm run models:bottle:skins`, действующий реестр — `shared/bottleSkins.json`,
метаданные новой поставки — `models/bottle/skin-delivery-v01.json`.

Численные проверки — `npm run test:bottle:lod`. В этой проверке границы и опора
в состояниях / переходах отличаются от HQ не более чем на 0,117 / 0,051 мм.
Отдельное сравнение экспортированных поверхностей (`scripts/check-bottle-low-surface.py`)
по 105 774 вершинам и центрам треугольников в двух направлениях показало максимум
0,296 мм, на корпусе — 0,128 мм. Это выборочная оценка поверхности, а не строгая
математическая верхняя граница Hausdorff distance. Переход на HQ меняет детализацию
материала, поэтому полное отсутствие воспринимаемой разницы требует приёмки владельцем.

### Подготовка оптимизированного HQ до отделения скинов

Входной HQ GLB стал на 77% легче исходного (в 4,34 раза), сетка — на 62% меньше.
Текущая упаковка отделяет его карты и материалы без изменения геометрии / пикселей.
Уменьшено количество окружных сегментов и повторяющихся рядов профиля; сохранены
исходные UV и нормали, непрерывные витки резьбы, крышка и её pivot. В GLB хранится
одна закрытая сборка для всех трёх runtime-состояний.

Нужные семь PBR-карт сохранены. Металл и бамбук уменьшены до максимальной стороны
512 px; normal / roughness покрытия остаются 512×512, как у исходного HQ.
Карты упакованы в стандартные PNG с палитрой 256 цветов: пять карт сохраняют
значения после resize точно; две normal-карты используют квантование палитры.
Для normal покрытия RMS ошибки RGB — около 1,61 / 1,27 / 0,46 из 255.
Формат не добавляет Draco / Meshopt / KTX / WebP-декодеров; исходное расширение
`KHR_texture_transform` сохранено для правильного масштаба материалов.

Воспроизведение подготовки из исходного защищённого master:

```sh
/Applications/Blender-4.5-LTS.app/Contents/MacOS/Blender --background --factory-startup \
  /Users/nsosin/Projects/source-3d/models/bottle/prepared-v02.blend \
  --python-exit-code 1 --python scripts/prepare-bottle-hq.py
python3 scripts/pack-bottle-hq.py
```

Используются установленный Blender и Pillow; установка пакетов командами не
выполняется. Editable source — `models/bottle/prepared-hq-v01.blend`,
метаданные / hashes / параметры карт — `models/bottle/hq-v01.json`.
Генератор проверяет неизменность исходного master и исходного HQ по SHA-256.

Повторный импорт реального GLB и выборочное сравнение 130 085 точек поверхности
дают максимум 0,0483 мм, на корпусе — 0,0347 мм. Для всех состояний и переходов
различие границ — до 0,0178 мм, опоры — до 0,0154 мм. Это измерения реальной
геометрии; выборочные проверки не являются строгим доказательством Hausdorff distance.

`scripts/compare-bottle-hq.mjs` сохраняет пять пар кадров из реального WebGL при
одинаковой камере / свете: общий стоя / лёжа, крупно покрытие, бамбук / крышка
и металл / резьба. Результаты — `.cache/qa/bottle-hq-v01/visual/`.
При просмотре фактура покрытия и общий силуэт сохранены; крупные планы металла
и бамбука немного отличаются детализацией. Финальная художественная приёмка
остаётся за владельцем. Случайная накопленная тень может отличаться между
рендерами; различие пикселей пола не измеряет потерю качества модели.
В выбранных внутренних областях предмета средняя абсолютная разница RGB
составила 0,58 из 255 на крупном плане покрытия, 1,30 на крышке и 2,13 на
горлышке. Области и статистика сохранены в `image-difference.json` рядом с кадрами;
это измерение пикселей выбранных областей, а не оценка восприятия всего изображения.

## Публичный JavaScript API

Единый объект — `window.appName3DVisualisation`. Все примеры выполняются
в консоли страницы. `sceneReady` завершается после проверки отдельного профиля,
а `ready` — после загрузки модели, применения сцены, окружения и тени.
Изменяющие методы и экспорт возвращают Promise и выполняются последовательно;
вызов до готовности ожидает `ready`. Ошибочные параметры отклоняются.

```js
const app = window.appName3DVisualisation;
await app.ready;
await app.setState('open');
// closed = стоит; open = крышка снята; lying = лежит.
// Примеры Ильи тоже работают: a = closed, b = open, c = lying.
```

Переход состояния сохраняет прежнюю предметную анимацию и завершает её
`defaultView` из каталога (в текущем v01 — Hero). Без каталога применяется
автоматическое вписывание; готовность модели не зависит от списка видов.
`prefers-reduced-motion: reduce` сразу устанавливает конечную позу.

```js
await app.viewsReady; // отдельная готовность каталога, не входит в app.ready
const views = app.getViews(); // id, label, camera для состояния и размера viewer
await app.setCamera(views.find(view => view.id === 'branding').camera);
const catalog = app.getViewCatalog(); // копия каталога, доступна до ready модели
await app.reloadViews(); // обновить список, сохранив текущую камеру / модель / скин

await app.setCamera({
  position: [3, 2, 8], target: [0, 1.2, 0], fov: 28, roll: 0,
  near: 0.025, far: 100, zoom: 1
});
const camera = app.getCamera(); // фактическая камера, включая ручное движение
const state = app.getState();
```

`setCamera` принимает `position`, `target` (массивы XYZ в координатах сцены),
опциональные `fov` в градусах, `roll` в градусах, `near`, `far`, `zoom`.
Пропорции viewport задаются его размером. Все готовые виды — полные объекты
этого контракта; их кнопки вызывают только публичный `setCamera(camera)`.
`getViews()` следует вызывать заново после смены состояния или размера страницы.
Без каталога он возвращает `[]`; его задержка или ошибка не блокирует другие
методы. `viewsReady` / `reloadViews` отклоняются отдельно, при ошибке обновления
последний рабочий список сохраняется. Подробный контракт —
[CAMERA_VIEW_DELIVERY.md](CAMERA_VIEW_DELIVERY.md).
Ручное вращение снимает выделение готового вида.

`getCamera()` дополнительно возвращает `quaternion`, `aspect`, `projectionMatrix`.
Это снимок реальной Three.js-камеры в момент вызова, не последний пресет.

```js
const png = await app.getCurrentViewAsImage(); // Blob, image/png, с нашего backend
const url = URL.createObjectURL(png);
const link = document.createElement('a');
link.href = url;
link.download = 'bottle.png';
link.click();
// После использования: URL.revokeObjectURL(url)
```

Метод возвращает Blob, не запускает скачивание самостоятельно. Кнопка страницы
вызывает этот же публичный метод и сохраняет полученный файл. При недоступности
backend показывается ошибка; клиентский снимок не используется как подмена.

## Скины через публичный API

```js
const skins = app.getSkins(); // 9 цветов: id, revision, подписи
await app.setSkin({ id: 'bottle-red', revision: 'v01' });
const selected = app.getSkin();
```

setSkin готовит набор до применения, сохраняет геометрию / камеру / позу /
логотип и завершается после показа. Новое ещё не применённое обращение
отменяет предыдущее с AbortError. Ошибка оставляет прежний скин; неизвестные
id / revision отклоняются. Выбор на low сохраняется при загрузке final.
Публичные операции и экспорт выполняются согласованно через очередь.
Полный формат, кеш / владение и проверки — [доставка скинов](SKIN_DELIVERY_DESIGN.md).

## Логотип и нанесение через публичный API

```js
const app = window.appName3DVisualisation;
await app.ready;
await app.setLogo(document.querySelector('input[type=file]').files[0]);
await app.setDecoration({surface: 'body', technique: 'pad', colors: 4, enabled: true});
const decoration = app.getDecoration();
await app.setDecoration({surface: 'lid', technique: 'doming'});
await app.setDecoration({enabled: false}); // сохраняет файл и выбранный метод
await app.setLogo(null);                  // убрать логотип
await app.setLogo('sample');              // вернуть пример
```

`getDecoration()` возвращает отдельную копию `{enabled, surface, technique,
colors, logo}`. `setDecoration` принимает частичное обновление без поля logo.
Поддерживаются методы из спецификации: корпус — laser / pad / screen / digital /
laser360 / sublimation; крышка — laser / pad / doming. Pad допускает 1–4 цвета,
screen — 1; для полноцветных и гравировальных методов colors равен 1 как служебное
значение. Изображение в полноцветном методе сохраняет все цвета.

При смене поверхности совместимый метод сохраняется, несовместимый заменяется
на laser. При смене метода количество красок ограничивается его максимумом;
явное неверное colors или несовместимые surface / technique отклоняются.
Зона и физический размер берутся из спецификации, UI показывает доступную область.
Растровая / PBR-визуализация способов нанесения повторно использует прежний код.

Смена поверхности выбирает ракурс логотипа из отдельного каталога текущего
состояния (либо его defaultView). Только изменение поверхности меняет ракурс;
смена файла / метода / красок / enabled сохраняет фактическую камеру.
Все изменения входят в общую очередь с состояниями, сценой, скинами, составом и PNG.
Перед применением viewer ждёт окончания жеста, движения и перехода качества,
после — обновления нанесения и теней. Canvas / rig / GLB не пересоздаются.
Более поздний setLogo отменяет ещё не применённый: старый ответ не вернёт удалённый
или заменённый логотип. Ошибка загрузки оставляет прежнее оформление.
Оформление общее у всех экземпляров бутылки текущей композиции, сохраняется low → final.

### Отдельная доставка файла логотипа

1. Браузер принимает SVG, PNG, JPG / JPEG, WebP, до 10 MiB и 40 MP.
   Исходник декодируется как изображение. Размер уменьшается пропорционально
   до 2048 px по большей стороне, без увеличения; альфа сохраняется в PNG.
2. `POST /api/logos`, `Content-Type: image/png`: нормализованные бинарные байты.
   Ответ — `{kind: "uploaded", sha256, width, height}`. Клиент сверяет SHA-256
   и размеры с отправленным изображением, затем применяет этот же растр в viewer.
   Raw SVG / HTML / URL не отправляются серверному worker.
3. Backend проверяет сигнатуру, CRC чанков, RGB/RGBA 8 bit, размеры ≤2048,
   отсутствие interlace / хвоста и ограниченную распаковку пикселей.
   Верхний лимит бинарного POST — 17 MiB. Повторный файл дедуплицируется по SHA-256.
4. Файлы лежат вне dist: `.cache/uploads/logos/<sha256>.png`, запись атомарна
   через temp в той же файловой системе. Сборка и перезапуск Node их не стирают.
   Каталог создаётся с mode 0700, файлы — 0600; подмена filesystem проекта
   блокирует новые записи. GET / HEAD `/api/logos/<sha256>.png` отдаёт PNG,
   `nosniff`, same-origin resource policy и private immutable cache / ETag.
5. PNG-задание версии 5 получает только logo-ref с hash / размерами, без имени
   пользовательского файла, произвольного URL и бинарных данных. До очереди backend
   проверяет наличие / соответствие. Worker загружает тот же файл с нашего origin,
   повторно проверяет SHA-256 / размеры и применяет те же материалы на final.

Иные refs — `{kind: "sample"}` и `{kind: "none"}`. Имя файла остаётся только
в интерфейсе текущего браузера. POST разрешён с того же origin либо с явно
настроенного `BOTTLE_ALLOWED_ORIGINS`, как API рендера.
Лимит локального хранилища — 64 уникальных файла / 64 MiB; повторная загрузка
уже известного файла доступна и при заполнении. На переполнение возвращается 507,
на неизвестный hash — 404, на несовпадение размеров / hash — 409. Автоматического
удаления нет. При переносе в production этот каталог должен находиться на постоянном
диске сервиса или заменяться эквивалентным объектным хранилищем с тем же контрактом;
нельзя считать build-dist или временную файловую систему местом хранения логотипов.
Ограничения исходника / нормализованного растра и ошибки переведены на DE/EN.

## HTTP-контракт

`POST /api/render`, `Content-Type: application/json`:

```js
const app = window.appName3DVisualisation;
await app.ready;
const camera = app.getCamera();
const image = camera.aspect >= 1
  ? { width: 1600, height: Math.round(1600 / camera.aspect) }
  : { width: Math.round(1600 * camera.aspect), height: 1600 };
const request = {
  version: 5, product: 'bottle', state: app.getState(), skin: app.getSkin(), scene: app.getScene(), composition: app.getComposition(), decoration: app.getDecoration(), camera, image
};
const response = await fetch('/api/render', {
  method: 'POST', headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(request)
});
```

`camera` целиком берётся из `getCamera()`; матрица и quaternion не заменяются
названием пресета или приближёнными значениями. Типы и проверка полей находятся
в `shared/renderContract.d.mts` и `shared/renderContract.mjs`.
Клиент передаёт состояние, skinId / revision, sceneId / revision / SHA-256,
описание composition с участниками и преобразованиями, decoration с выбранным нанесением и ссылкой на загруженный логотип,
параметры камеры и размер; URL моделей, HTML,
скрипты, скриншоты и сырые пользовательские файлы контракт рендера не принимает.
Логотип доставляется отдельным PNG-запросом, описанным ниже.

Ответ: PNG, `Content-Disposition: attachment`, `Cache-Control: no-store`.
Заголовки `X-Render-Engine: server-chromium`, `X-Render-Id` и
`X-Render-Camera-SHA256`, `X-Render-Skin`, `X-Render-Scene` и `X-Render-Scene-SHA256`
позволяют проверить происхождение и параметры результата. Сервер сравнивает
фактические камеру, сцену, скин, состав и оформление worker
с запросом до возврата файла.

`X-Render-Composition-SHA256` подтверждает канонический состав / преобразования
участников; сервер сверяет результат worker, публичный метод проверяет hash ответа.

Версия 1 без skin поддерживается как фиксированный чёрный вид. Skin в версии 1
отклоняется. В версии 2 skin обязателен. Обе версии используют сохранённую сцену
`source-studio@v01`, поле scene в них запрещено. В версии 3 scene обязателен;
неизвестная сцена получает 404, несовпадающий hash — 409 до очереди рендера.
Подмена неизвестной ревизии default-профилем не выполняется.

Версия 4 требует composition. В версиях 1–3 состав фиксирован одной бутылкой,
поле composition в них запрещено. Типы и ограничения, групповой PNG, поддержка
адаптеров и примеры API — [COMPOSITION_CAMERAS.md](COMPOSITION_CAMERAS.md).

Версия 5 требует decoration, включая logo-ref. Версии 1–4 сохраняют прежний
демонстрационный логотип / body / laser / 1 цвет и запрещают инъекцию decoration.
Версия 4 продолжает принимать явную composition. Header
`X-Render-Decoration-SHA256` подтверждает канонический JSON всего оформления;
renderer проверяет результат worker, публичный метод проверяет ответ backend.

## Сцена через публичный API

```js
await app.sceneReady;
const scene = app.getScene(); // id, revision, sha256
const profile = app.getSceneProfile(); // копия описания
await app.setScene({id: 'source-studio', revision: 'v01'});
```

Смена сцены использует общую очередь, ждёт завершения жеста и подготовки света /
теней, сохраняет модель / камеру / позу / скин. GLB и карты товара повторно
не загружаются. Формат профиля, активный указатель и эксплуатация —
[SCENE_DELIVERY.md](SCENE_DELIVERY.md).

Изображение страницы имеет длинную сторону до 1600 px, увеличение до 2× от CSS,
с сохранением пропорций камеры. HTTP-контракт допускает 64–2048 px по стороне,
не более 2048² пикселей. Сама матрица проекции сохраняется без пересчёта по округлённым
размерам изображения; поэтому оптика и композиция совпадают с исходной камерой.

Ошибки возвращаются JSON-объектом `error`: 400 — параметры, 403 — чужой / невалидный Origin,
405 — метод, 413 — тело >16 KiB, 415 — формат, 429 — заполненная очередь,
500 — внутренняя ошибка без раскрытия деталей, 503 — рендер недоступен,
504 — превышено время выполнения. Для JSON требуется точный тип
`application/json` (регистр и параметры charset допустимы); JSONP не принимается.
Слишком большое тело получает JSON с 413 до закрытия соединения, включая chunked
запрос без Content-Length. Невозможная перспективная матрица и нестроковое состояние
отклоняются до очереди; допустимая off-axis матрица сохраняется без пересчёта.

## Как работает сервер

Node-сервер `server/start.mjs` обслуживает страницу и API с одного origin.
`server/renderer.mjs` последовательно выполняет максимум три принятых задания
(включая активное), с лимитом 90 секунд на выполнение, включая запуск Chromium
и создание context; ожидание очереди в этот лимит не входит. Собственный headless
Chromium открывает только заданный сервером `/render.html`, загружает final
geometry GLB, manifest и карты выбранного скина,
фиксирует состояние и устанавливает точные position / quaternion / projectionMatrix.
Затем общая студия рассчитывает окружение, тени и постобработку и выдаёт PNG.
Отдельный browser context закрывается после задания; Chromium закрывается после
60 секунд простоя или при остановке сервера. Внешние сетевые запросы worker запрещены.
После сбоя / отключения Chromium или ошибки задания следующее задание запускает
новый браузер. Поздно созданные после таймаута context / browser закрываются;
остановка сервера отменяет активное задание и не запускает очередь заново.

`GET /api/health` сообщает режим сервера и счётчики очереди / завершённых рендеров.
Этот endpoint не запускает Chromium и не заменяет реальную проверку рендера.

## Production-режим

```sh
npm run build
PORT=5181 npm start
# http://127.0.0.1:5181/bottle.html
```

Сборка содержит прежний `index.html`, новый `bottle.html`, внутренний `render.html`
и локальные ассеты. Production-сервер раздаёт только `dist/`, API остаётся тем же.
Комплект приложения включает `dist/`, `server/`, `shared/`, `config/camera-views/`, `config/scenes/`, `package.json`,
`package-lock.json`, `models/bottle/specification.json` (общая проверка зон / методов)
и установленные runtime-зависимости; один `dist/` backend не содержит.
На выбранном сервере должны быть совместимый Chromium, его системные библиотеки
и зафиксированные runtime npm-зависимости. Установка окружения выполняется
отдельным разрешённым действием; сервер не скачивает ничего при запуске.

Публичное подключение, TLS / reverse proxy, авторизация, лимиты инфраструктуры,
домен и выкладка определяются при выборе production-окружения. GitHub Pages
обслуживает только статические файлы и не выполняет этот Node-backend.
Публикация существующего Pages-стенда этой работой не выполняется.

### Отдельный frontend на GitHub Pages

Для публикации `/bottle.html` отдельно от Node-сервера в **готовый HTML этой
страницы** добавляется публичный адрес API:

```html
<meta name="s3dlabs-api-origin" content="https://backend.example.com">
```

Без meta используется прежний API относительно страницы. `src/apiUrl.ts` применяет
настройку к камерам, сценам, загрузке / доставке логотипов и рендеру. Геометрия,
скины и текстуры остаются относительно frontend. Допускается HTTPS origin без
пути, параметров и credentials; HTTP разрешён только для локальной проверки.
Meta не добавляется в `render.html`: внутренний Chromium получает GLB, сцены и
логотипы с собственного сервера, без обхода через публичный туннель.

На backend явно задаётся origin страницы:

```sh
BOTTLE_ALLOWED_ORIGINS=https://nicsosin-progovori.github.io PORT=5181 npm start
```

Пустое значение сохраняет прежнее поведение. `server/cors.mjs` разрешает только
перечисленные HTTP(S) origins, обрабатывает preflight GET / HEAD / POST и открывает
для чтения fingerprint-заголовки сцен / PNG. Wildcard, credentials и произвольные
заголовки не разрешены. Origin для POST проверяется по тому же списку.
Неподходящий origin не получает разрешения CORS; ограничения upload / render
и очередь сохраняются.

GitHub Pages публикует статические файлы и не исполняет Node / Chromium.
Для полной демонстрации нужен доступный HTTPS backend: временный локальный
сервер с туннелем либо отдельное размещение. Наличие исходников и сборки ещё
не означает, что новая страница опубликована. Адрес backend и выпуск должны
быть проверены до push; в Pages отправляется только подготовленная веб-сборка,
без `src/`, `server/`, Blender-исходников, `.cache/` и credentials.

Для текущей публикации выбран существующий Selectel / `3d.progovori.ru`, без
новой VM. Фактическое состояние, ограничения, версия и откат ведутся в
[SELECTEL_DEPLOYMENT.md](SELECTEL_DEPLOYMENT.md). На 03.11 серверные операции
приостановлены для восстановления ПРОГОВОРИ; публичная новая бутылка ещё
не запущена. Последний Linux-кандидат не прошёл PNG-тест (HTTP 504 / 90 s).
Дальнейшая оптимизация worker проверена локально и требует повторной Linux-проверки.

## Проверки

Общие команды для всей текущей ветки:

```sh
npm run test:unit
npm run typecheck
npm run build
npm run test:e2e
```

`test:unit` выполняет все Node-тесты из `scripts/` и `tests/`.
`test:e2e` выбирает только `*.spec.ts`, запускает отдельный API + Vite на 5180
и останавливает их после прогона. Занятый порт не переиспользуется автоматически.
`THREEDLABS_TEST_URL` либо прежний `BOTTLE_TEST_URL` явно выбирает уже работающий
сервер; тогда запуск / остановка этого сервера остаётся за вызывающим.
Набор включает прежний каталог, пару, новую бутылку, сетевые ошибки и отказ
localStorage. Недоступность хранилища не блокирует интерфейс: язык работает
в текущем сеансе без сохранения; начальный язык в этом случае немецкий.
Для файлов тестов используется `THREEDLABS_TEST_OUTPUT` либо `.cache/qa/e2e/tests`.

Отдельные проверки подсистем:

```sh
npm run test:bottle:api
npm run test:bottle:lod
npm run test:bottle:skins
npm run test:bottle:cameras
npm run test:bottle:scenes
npm run test:bottle:composition
npm run test:bottle:branding

node /Users/nsosin/Projects/source-3d/node_modules/@playwright/test/cli.js test -c playwright.bottle.config.ts
```

Последняя команда запускает собственный headless браузер для автоматических тестов
этого приложения. Установка браузера не входит в команды проверки.
Актуальные результаты инженерной проверки — в разделе контроля качества README.

Для уже запущенной production-сборки можно повторить необходимые сценарии
с `BOTTLE_TEST_URL=http://127.0.0.1:5181` перед последней командой и списком
`tests/bottle-api.spec.ts tests/bottle-progressive.spec.ts tests/bottle-skins.spec.ts tests/bottle-cameras.spec.ts tests/bottle-scenes.spec.ts tests/bottle-composition.spec.ts tests/bottle-branding.spec.ts tests/render-startup.spec.ts`.

с dev-сервером, а не из `dist/`.

`BOTTLE_TEST_URL` на production-сборку: скорость dev-модулей не выдаётся за метрику выпуска.
Весь набор нового контура для собранного сервера, без dev-only импорта транспорта:

```sh
BOTTLE_TEST_URL=http://127.0.0.1:5181 npm run test:e2e -- \
  -c playwright.bottle.config.ts \
  --grep-invert 'model download survives an interrupted transfer'
```

`BOTTLE_EVIDENCE_DIR` задаёт отдельное место результатов; по умолчанию это
`.cache/qa/bottle-api/`. Тестовый HTML и `dist/` исключены из наблюдения dev-сервера,
чтобы запись результатов не перезагружала страницу.

Контракт камеры проверен по [документации Three.js](https://threejs.org/docs/pages/PerspectiveCamera.html),
запуск headless worker — по [Playwright BrowserType](https://playwright.dev/docs/api/class-browsertype#browser-type-launch).

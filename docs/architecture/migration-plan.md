# План: DevOps-харнесс, переезд в app/, рендер-галерея, единый плеер (черновик)

_Ничего не реализуем, пока владелец не даст команду (надиктовано с телефона;
реализация — когда он будет за компьютером). Правило: в git не коммитим сами;
каждая фаза — отдельный шаг с точкой проверки._

## Зафиксированные решения
- **School B**: devops сверху, приложение — в подпапку.
- Имя подпапки — **`app/`** (обоснование ниже).
- Два сервиса: **`web`** (лёгкий: dist + API + оркестрация) и **`renderer`**
  (тяжёлый: Node + Chromium).
- **Reverse proxy + TLS** — только оснастка (`ops/`), в dev не нужен, в код
  разработки не лезет (prod/edge-профиль compose).
- **Vite — только dev/сборка.** «Отдельный контейнер под Vite» = builder-стадия
  образа (эфемерная, живёт лишь во время сборки). Прод ставится `--omit=dev`; Vite в
  проде не нужен, т.к. в рантайме работает только собранный `dist`. То есть «можно ли
  поставить приложение без dev-части и чтобы заработало» — да, при условии, что
  `dist` уже собран (его и собирает builder-стадия).
- **Renderer — асинхронная галерея**, не онлайн-рендер (см. `rendering-async.md`).
- **index.html + bottle.html → один динамический плеер** (разбор ниже).

## Почему `app/`
Единого стандартного имени для Vite+React нет (обычно приложение = корень репо). При
выносе из-под devops распространены `app/`, `web/`, `client/`. Здесь в одной базе и
фронт (`src`), и бэк (`server`), и контракты (`shared`) — поэтому `app/` как
контейнер ВСЕГО приложения уместнее, чем `web/` (тот подразумевал бы только фронт).
Фреймворк — **не Next.js**: это Vite + React (MPA, 3 входа) + свой Node-сервер;
ближе всего к «Vite React + Node API». Внутри `app/` позже при желании выделим
`web/` + `server/`.

## Разница index.html и bottle.html (факт из кода)
- `index.html → App` — общий **мультипродуктовый** студийный конфигуратор (все
  товары, выбор `?model=`, загрузка логотипа, размещение, i18n). Динамичный, но
  клиентский и «широкий».
- `bottle.html → BottleApiPage` — специализированная страница ОДНОГО продукта
  (бутылка), доведённая до полного контрактного пайплайна: публичный API, каталог
  камер по API, сцена по API, серверный PNG, декор/скин по контрактам. Это
  эталон-реализация, а **не** «захардкоженные сорсы».

Вывод: это не «динамический index vs захардкоженный bottle». Наоборот — App широкий
но неглубокий, BottleApiPage глубокий но на один продукт. **Цель** — слить в ОДИН
динамический, контрактно-управляемый плеер (как BottleApiPage, но продукт-
независимый), в который «засовываешь» нужный объект. **Зависимость**: единый плеер
требует per-product delivery-адаптеров (сейчас только bottle) — поэтому полное
слияние идёт по мере переноса продуктов в контракты; вблизи — унифицируем оболочку,
bottle = первый объект в ней.

## Фазы (каждая — с точкой проверки, где можно проверить меня)
### Фаза 1 — DevOps-харнесс `ops/` (код на месте)
`ops/bin/` (up/build/sh/logs/test); `ops/docker/` (Dockerfile.web,
Dockerfile.renderer, docker-compose.yml с профилями `dev`/`prod`,
Dockerfile.dockerignore); параметризация env; `ops/selectel/` остаётся оверлеем;
proxy+TLS только в prod-профиле.
**Проверка 1:** `docker compose --profile dev up` поднимает web+renderer;
`/api/health` зелёный; один PNG рендерится; `npm run test:unit` проходит.

### Фаза 2 — Переезд кода в `app/` (детальный план, НЕ выполнено)
Переносим через `git mv` (сохраняем историю, у владельца чистый diff-rename).

**Переезжает в `app/`:**
- Папки: `src/ server/ shared/ config/ models/ public/ scripts/ tests/`
- Файлы: `index.html bottle.html render.html favicon.svg package.json
  package-lock.json vite.config.ts tsconfig.json .nvmrc playwright.config.ts
  playwright.bottle.config.ts`

**Остаётся в корне:** `ops/ docs/ README.md AGENTS.md .gitignore .git .idea`.

**Что НЕ требует правок (пути относительные и переезжают вместе):**
`vite.config.ts` (input/base), `tsconfig.json` (`include: src`), `server/start.mjs`
(root вычисляется от своего расположения), `playwright*.config.ts`, скрипты
`package.json`. `.gitignore` — паттерны без ведущего слэша (`node_modules/`,
`dist/`, `.cache/`) матчатся на любой глубине → менять, скорее всего, не нужно.

**Что правим:**
- `ops/docker/Dockerfile`: источники с префиксом `app/` (контекст остаётся корнем):
  `COPY app/package.json app/package-lock.json ./`, `COPY app/ ./` (deps),
  и в runtime — `COPY app/server ./server` и т.д.; `COPY --from=builder /app/dist` без изменений.
- `ops/docker/Dockerfile.dockerignore`: `**/node_modules`, `**/dist`, `**/.cache`
  (чтобы `app/node_modules` не раздул контекст); `app/tests` НЕ игнорировать (нужны стадии `deps`).
- Доки с путями (`environment.md`, `project-anatomy.md`, `04-scene.md`, `interfaces.md`,
  `AGENTS.md`): `src/ server/ config/ …` → `app/…`.
- `ops/selectel/Dockerfile` — устаревает в пользу `ops/docker/`; помечаем deprecated.
- Dev-команды теперь из `app/`: `cd app && npm run dev:bottle`.

**Точка проверки 2:** `ops/bin/up` пересобирается, web+renderer健康; `ops/bin/test`
зелёный; `/bottle.html` грузится, PNG-экспорт работает; parity-PNG не изменился.
**Откат:** всё через `git mv` и без коммита — `git restore`/`reset` возвращает.

**Решения к ревью перед стартом Фазы 2:**
1. `assets/` + `.nojekyll` (закоммиченные артефакты сборки GH Pages, ни один HTML на них
   не ссылается): удалить из исходников (регенерировать при сборке) / оставить в корне /
   перенести? — рекомендация: удалить из source, GH Pages собирать из `dist` при деплое.
2. Папка «Claude outputs» (мои схемы, не в git): удалить или перенести в
   `docs/architecture/diagrams/` + добавить в `.gitignore`.

### Фаза 3 — Renderer как асинхронная галерея
Очередь задач + пул воркеров + хранилище результатов (ключ = fingerprint) + подписка
на готовность; `web` только ставит задачу и отдаёт галерею (см. `rendering-async.md`).
**Проверка 3:** логотип → задача → галерея; повтор → попадание в кэш.

### Фаза 4 — Единый динамический плеер
Слить index+bottle в один контрактно-управляемый плеер; обобщать за пределы бутылки
по мере адаптеров.
**Проверка 4:** один вход рендерит ≥2 разных объекта по дескриптору.
